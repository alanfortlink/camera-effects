# System-wide camera effects on Omarchy — achievability research (2026-08-16)

Goal: replicate macOS "Video Effects" (Center Stage, Portrait, Studio Light, Reactions, background replace, Presenter Overlay) as a layer *below* every app, with the toggle/preview UI living in the Omarchy Quickshell shell (like the Control Center camera pane). This document is research only — nothing implemented.

Verdict up front: **achievable**, and this machine already has every load-bearing piece (PipeWire 1.6.8 + WirePlumber 0.5.15, v4l2loopback 0.15.4 loaded, Quickshell 0.3 with QtMultimedia working, RTX 2080 Ti + onnxruntime-cuda + OpenCV 5, GStreamer 1.28 with pipewire/nvcodec plugins). The two things macOS gets "for free" that we must build ourselves are (1) a single choke point in the camera stack — Linux has two (PipeWire and raw V4L2), so the daemon must publish the processed feed on both — and (2) hiding/renaming the raw camera so apps default to the processed one. Nothing existing on Linux is a drop-in; the closest are `nvidia-broadcast-linux` (Python, GPL) and the abandoned `LinuxStudioEffects` (Rust daemon + GNOME menu).

## 1. What was verified on this machine (spikes, not implementation)

- `qs -p` with `import QtMultimedia` inside a layer-shell `PanelWindow`: `MediaDevices` enumerated the C930e, `Camera`+`CaptureSession`+`VideoOutput` rendered 1920x1080 live frames. **Quickshell can show a live camera preview natively.** Qt's ffmpeg backend enumerates **V4L2 devices only** (id = `/dev/video0`); it does not see PipeWire-only nodes.
- Feeding `/dev/video10` (v4l2loopback, `exclusive_caps=1`) from `gst-launch pipewiresrc ! … ! v4l2sink`: sysfs `state` flips `output→capture`, Qt immediately lists "OBS Virtual Camera" as a second camera. **But WirePlumber did not create a PipeWire `Video/Source` node for it** — it probed the device at boot as output-only and does not re-probe on `udevadm trigger --action=change`; only a root `remove`+`add` uevent made "OBS Virtual Camera (V4L2)" appear (and the node then persists even after the feed stops). Consequence: PipeWire/portal consumers (Firefox-with-pipewire, Chromium-with-flag, OBS pipewire source, GTK apps) won't see a v4l2loopback camera unless it advertises capture caps at enumeration time (`exclusive_caps=0`), or the daemon triggers a re-probe. (Side effect of the spike: a stale "OBS Virtual Camera (V4L2)" node now exists in this PipeWire session until WirePlumber restarts — harmless.)
- Native PipeWire virtual camera: `gst-launch pipewiresrc target-object=<cam> ! videoconvert ! pipewiresink stream-properties='props,media.class=Video/Source,media.role=Camera,node.name=camfx.virtual,node.description=OmarchyCameraFX'` produced a proper `Video/Source` node instantly, no root, no kernel module. This is the modern path ("PipeWire is the new v4l2loopback", Laurent Pinchart, Feb 2026).
- Chromium 151 here still ships `WebRtcPipeWireCamera` / `enable-webrtc-pipewire-camera` as a **flag** (not enabled in this profile), i.e. Chromium/Electron (Discord installed) read cameras via raw V4L2 today → v4l2loopback is still required for "system-wide".
- Quickshell's `Quickshell.Services.Pipewire` tracks nodes with `PwNodeType` flags including `Video`, `Stream`, `Source`, `Sink`, exposes `PwLink.source/target` and `PwNode.properties` — enough to detect "app X is linked to camera Y" for PipeWire consumers from QML. omarchy-shell already uses this service for audio.
- `pipewire-v4l2` (`pw-v4l2` LD_PRELOAD shim, lets V4L2 apps read PipeWire nodes) is **not installed**; it exists in Arch as `pipewire-v4l2` and is a per-app opt-in, not a system-wide answer.
- Omarchy shell (`~/.local/share/omarchy/shell`) is a single Quickshell instance with a manifest-based plugin system (`bar-widget`, `panel`, `service`, `overlay`), IPC summon (`omarchy-shell shell summon <id> '<json>'`), bar indicators (e.g. `ScreenRecording.qml` polls a process) — a "camera" bar indicator + panel + service plugin fits the existing conventions exactly.

## 2. Quickshell / Omarchy shell side (setup + preview UI)

- Live preview: `import QtMultimedia` in a Quickshell `PanelWindow` works (verified here; other shells do it — Ambxst `MirrorWindow.qml`, noctalia `Mirror.qml`, DMS/caelestia video wallpapers). Wrap it in a `Loader { active: panelOpen }` so the camera is only opened while the pane is visible.
- Qt Multimedia 6.11 camera backend on Linux is **V4L2 only** (Qt's PipeWire code covers audio + portal screen capture, no camera). So the shell previews the processed feed by opening the **v4l2loopback** device (formats fine: YUYV/NV12/RGBA…), not the PipeWire node. Because Qt re-enumerates only on `/dev` add/remove, an `exclusive_caps=1` loopback that starts streaming later can be missing from `MediaDevices.videoInputs` — re-create the `MediaDevices`/`Camera` on open, or run the loopback with `exclusive_caps=0`. Alternative if needed: `qt6-multimedia-gstreamer` backend + `pipewiredeviceprovider` (untested).
- Known risk: QtMultimedia inside the long-running shell also instantiates Qt's PipeWire audio monitor; quickshell issue #859 (Qt 6.11.0 crash in `QAudioDeviceMonitor`) and #730/#770. Mitigation: keep the preview in an on-demand plugin, or run the preview/setup UI as a separate `qs -c` process (like macOS's separate Control Center pane), talking to the same daemon.
- "Camera in use" detection (to show the green camera indicator / summon the pane like Control Center): for PipeWire consumers, `Quickshell.Services.Pipewire` — filter nodes with `type & PwNodeType.Video && !isSink`, `PwNodeLinkTracker { node: cam }` gives who's linked; `Stream/Input/Video` consumer nodes are `Untracked` type but still appear in `Pipewire.nodes` and `PwLink.target`, and `PwNode.properties` (bound via `PwObjectTracker`) gives `application.name`. For raw-V4L2 consumers (Chromium/Electron/Zoom) the shell can't see it; the daemon can (inotify `IN_OPEN/IN_CLOSE` on `/dev/videoN`, or v4l2loopback sysfs `state`/opener count) and report over IPC. Omarchy's audio panel comment warns reading `properties` during node churn destabilized the service — snapshot on a timer as it does.
- Control channel shell⇄daemon: no generic DBus QML API in Quickshell 0.3 (only internal plumbing; PR #484 open). Use `Quickshell.Io` `Socket` (unix socket + `SplitParser`), `Process` (`busctl`/CLI), `FileView` (`watchChanges`, `JsonAdapter` on the daemon's state file), or the daemon calls `omarchy-shell <target> <method>` (`qs ipc call`, plus `qs ipc listen` for signals, new in 0.3.0). Omarchy plugin: `~/.config/omarchy/plugins/<id>/manifest.json`, kinds `bar-widget` (indicator + popup, like Audio) / `panel` (`keepLoaded: true` like OSD) / `service` (headless singleton) — a `camera` plugin = bar indicator that appears when a camera is active + effects pane with preview and toggles + service that watches PipeWire links.
- Alternatives for preview if QtMultimedia proves flaky: daemon renders its own layer-shell/xdg window (GStreamer `waylandsink`, SDL) toggled by shell IPC (Quickshell could even `ScreencopyView` a toplevel via hyprland-toplevel-export); `qml6glsink` isn't reachable from pure QML; frames-over-socket into `Image` only for low fps.

## 3. The effects themselves (RTX 2080 Ti / CUDA)

Common stack: onnxruntime 1.28 CUDA EP (IOBinding + CUDA Graphs; TensorRT EP for heavier nets — TensorRT 10 still supports Turing SM 7.5, "TensorRT-RTX" doesn't) + OpenCV 5 `cv::cuda` for resize/warp/blur/composite (GpuMat wraps as ORT device OrtValue, zero copy). MediaPipe's own runtime is CPU-only on desktop Linux wheels; use its `.tflite` models converted to ONNX (PINTO_model_zoo, Apache-2.0). Camera frames (MJPEG/YUYV) are CPU-decoded then one pinned H2D copy (~<1 ms at 1080p); everything else stays on GPU; output to v4l2loopback needs one D2H. NVIDIA Maxine VFX SDK: Linux build exists (0.7.7, Turing OK) but is now gated behind AI Enterprise; Windows SDK is free — not a practical base. Budget estimates on 2080 Ti: selfie seg <2 ms, YuNet ~2 ms, hands 5–8 ms, Depth-Anything-Small 15–25 ms, BiRefNet-lite@512 25–40 ms, RVM MNv3 720p ~10 ms → 1080p30 with mask+blur+framing fits; run heavy nets at reduced rate on a second stream.

| macOS effect | Recommended | Notes |
|---|---|---|
| Portrait / background blur & replace | MediaPipe selfie segmentation (landscape 144×256 or `selfie_multiclass_256x256`, Apache-2.0, ~106K params) as always-on mask; upgrade path BiRefNet-lite-matting (MIT) for hair/alpha; RVM only if GPL is acceptable; MODNet weights are non-commercial | Post-process like Meet/obs-backgroundremoval: EMA on mask, guided/joint-bilateral upsample against full-res frame, per-pixel blur ∝ mask, light wrap for replacement. Optional depth-aware blur via Depth Anything V2/V3 Small (Apache-2.0) at 10–15 Hz. Intensity slider like Sonoma. |
| Center Stage | YuNet (OpenCV, BSD-3, ~2 ms) or BlazeFace at 10–15 Hz + tracker; non-ML framing rules | Target = union of faces expanded to head+shoulders (~3× face height, ~0.5× headroom), fixed aspect, zoom clamped ~1–2.5× (needs >1080p sensor to avoid mush), deadband ~5%, separate critically-damped smoothing for pan (τ≈0.3–0.5 s) and zoom (τ≈1 s, zoom-out faster), hold ~1–2 s on loss, `cv::cuda::warpAffine` bicubic. |
| Studio Light | No usable open real-time relighting model (DPR unclear license, Lite2Relight unverified, IC-Light seconds/frame). Do what Apple visibly does: lift/soft-light the face region (skin/hair classes of `selfie_multiclass`), mild smoothing, darken background ~0.5–1 EV + vignette; optional fake key light from depth normals | One intensity slider. |
| Reactions | MediaPipe Hand Landmarker (Apache-2.0, ONNX via PINTO) + small MLP on 21 normalized landmarks (kinivi / PINTO gesture recognizers, Apache-2.0) + geometric rule for two-hand heart; HaGRIDv2 (33 classes incl. heart/rock/peace) is stronger but weight licence unclear | Apple gesture set: hearts (two-hand heart), thumbs up/down, balloons (one peace), fireworks (two thumbs up), rain (two thumbs down), confetti (two peace), laser (two rock-horns). Trigger: class stable ~20–30 frames, hands away from face, cooldown ~5 s, overlay ~3 s. Overlay compositing on GPU. |
| Presenter Overlay | Same person mask composited over PipeWire/xdg-desktop-portal screencast (Large: person in front of scaled window; Small: movable bubble) | Bigger scope: needs screencast session + producing a second virtual "camera" or a screen-share source. |

## 4. Existing Linux projects (none is a drop-in; what to borrow)

- `nvidia-broadcast-linux` (Hkshoonya, GPL-3, Python/GTK4, active Aug 2026, 111★): GStreamer capture → RVM/IS-Net/BiRefNet + CUDA fused kernels → v4l2loopback; blur/replace/greenscreen, auto-frame, eye contact, relighting, denoise, virtual mic. Most complete NVIDIA-oriented open effect set; proof the effects run on Linux+CUDA; Python.
- `obs-backgroundremoval` (locaal-ai, active, 4.4k★): best-maintained ONNX Runtime CUDA/TensorRT segmentation code + models; output only via OBS virtual cam. Borrow model handling.
- `LinuxStudioEffects` (WilliamFriconneau, Rust GStreamer appsrc/appsink + ORT + GNOME Shell menu, last commit Jan 2026, 0★): closest architectural match (daemon + DE menu, auto-teardown when no consumer) but an abandoned scaffold.
- `camfx` (Ankk98, Python MediaPipe, D-Bus effect chain, GTK GUI, Mar 2026), `linux-studio-effects` (ericjchang, Intel NPU/OpenVINO only), `Linux-Fake-Background-Webcam` (Python/CPU, reference only), `Blucast` (Maxine wrapper, needs gated SDK), `webcamoid` (Qt6, 60 classic filters, no ML, own akvcam module), `backscrub` (dead). Minimal native-PipeWire-virtual-camera references: `Meeting-BaaS/pipewire-virtual-camera` (Rust, pipewire-rs), `pipewire_video_tests` (C).
- GStreamer 1.28: `onnxinference`/LiteRT elements, `GstTensorMeta`, segmentation decoders, `gstcuda`/`nvcodec` — a viable pipeline skeleton (`pipewiresrc → onnxinference(TRT EP) → custom composite → pipewiresink + v4l2sink`), but no stock person-matting compositor; you write that element.
- Kernel virtual-camera RFC (linux-media, Feb 2026) was pushed back toward PipeWire; KDE Linux dropped v4l2loopback-utils (May 2026). PipeWire 1.6's ONNX/FFmpeg filter-graph is audio-only; Vulkan video converters are roadmap. No DE (GNOME/KDE/Hyprland) ships a camera-effects UI; no commercial Linux product (Camo/VCam/mmhmm/NVIDIA Broadcast) exists.

## 5. How macOS / Windows actually do it (what to mirror)

macOS: effects are a "system-level camera feature, available in your apps with no code changes" (WWDC21 10047, WWDC23 10105). Frames come from the camera daemon (`cameracaptured`, formerly VDCAssistant; `appleh13camerad` drives the ISP), but the effect rendering itself runs **inside each client app's process** in Apple's private AVFCapture layer (Portrait.framework / VideoProcessing.framework, Metal+CoreML/ANE — visible in third-party app crash/profiler stacks, dev forums 778257/751861). Settings are **per app (bundle ID)**, not per camera, persisted in the secure-control-center prefs plist (`videoeffects/<bundle-id>/…`) and read via an XPC service; Control Center presents an on/off toggle per app. Users decide, not apps ("a user decision, not an app decision", thread 805786); apps only get `isXActive` KVO, `centerStageControlMode`, `showSystemUserInterface(.videoEffects)` deep link, `Info.plist NSCameraReactionEffectGesturesEnabledDefault`. Costs: gesture detection runs in every camera app even with Reactions off; effects cap output at 1920×1440 / 30 fps and are skipped for compressed or larger streams (that's how CMIO virtual cameras opt out). UX: Sonoma+ green camera menu-bar item appears when any app runs a camera (CMIO "device is running somewhere"), shows app+camera, live preview (manual pan/zoom when Center Stage off), Center Stage, Portrait (+intensity), Studio Light (+intensity), Background (Sequoia), Reactions (8 buttons), Mic Mode, Presenter Overlay (Small/Large), Desk View. Third-party virtual cameras are CoreMediaIO Camera Extensions (WWDC22 10022): sandboxed extension republishing frames through `registerassistantservice`, which enforces TCC. Hardware gating: Apple silicon / iPhone 12+ Continuity Camera.

Windows Studio Effects: the closest analogue to what we'd build. The WSE driver package (Microsoft Effects Pack) is chained as the **last stage of the camera driver stack**, replacing the real camera with a "composite" camera; NPU-hosted; "once an effect is turned on it is on by default for any app using the camera, even if the app doesn't know about it" — per-camera per-user defaults applied at stream start (Settings › Cameras with preview, Quick Settings "Studio effects" flyout, `ms-settings:camera?cameraId=`), apps may change current values via KS extended properties (`BACKGROUNDSEGMENTATION`, `EYEGAZECORRECTION`, `DIGITALWINDOW` framing, WSE set: STAGELIGHT, CREATIVEFILTER, AUTOMATICFRAMINGKIND…), constraints: single NV12 stream 640×360–2560×1440, 15–30 fps, passthrough profile bypasses effects.

Takeaways for Linux: (a) do the Windows shape — a composite/virtual camera that replaces the raw one below all apps, per-camera user defaults, on-demand pipeline; (b) copy the macOS UX — indicator only while a camera is in use, preview + toggles + intensity sliders, per-app awareness where PipeWire tells us the app; (c) keep the raw camera reachable for opt-out (Apple's "compressed/large stream" trick ≈ our hidden-but-openable raw node), and cap the processed stream at 1080p30 NV12/YUYV like both vendors.

## 6. Linux plumbing facts that shape the design (2026-08)

- Consumers: Chromium/Chrome — PipeWire camera exists since M127 but is still `FEATURE_DISABLED_BY_DEFAULT` in main (M153; `WebRtcPipeWireCamera`, `chrome://flags/#enable-webrtc-pipewire-camera`); Firefox — `media.webrtc.camera.allow-pipewire` still `false` upstream (Fedora flips it since F41); Electron (Discord/Slack/Teams/VS Code) — V4L2 (feature flag possible per app, untested); Zoom — V4L2 only, needs `exclusive_caps=1`; OBS — has a "Camera (PipeWire)" *source* since 30.1 but virtual-cam *output* is v4l2loopback only (PipeWire virtual-cam PR #5377 unmerged since 2021); Qt Multimedia — V4L2; Wine — V4L2; GNOME Snapshot — portal; SDL3 — has PipeWire camera. **Net: on this host every real consumer reads V4L2 → v4l2loopback (`exclusive_caps=1`) is mandatory; a native PipeWire node is the forward-looking second output.**
- Camera portal (`org.freedesktop.portal.Camera`): xdp `AccessCamera` (permission store `devices/camera`, GTK access dialog) + `OpenPipeWireRemote` hands the app a PipeWire socket with `media_roles=Camera`; WirePlumber `find-portal-access.lua` grants portal clients only nodes with `media.class=Video/Source` **and** `media.role=Camera`. libwebrtc additionally requires `node.description` and only accepts `EnumFormat` pods with **fixed** format+size (`SPA_CHOICE_None`; framerate may be range/enum); accepted formats I420/NV12/YUY2/UYVY/RGB*/MJPG; DmaBuf/MemFd/MemPtr. So the daemon must publish one fixed-size EnumFormat per (format, WxH) — PipeWire's `video-src.c` example (rectangle range) would be ignored by browsers.
- Known 1.6.x bugs to watch: pipewire#5165 (2026-03, `pipewiresink mode=provide` → black/crash loop in browsers), #5412 (2026-08, PW 1.6.8 Arch "no more output formats"), #5378 (provide-mode node wedges after a SIGKILLed consumer). A native `pw_stream` provider with proper fixed formats is the safer path than GStreamer `pipewiresink`.
- Hiding the raw camera: WirePlumber `monitor.v4l2.rules` (and `monitor.libcamera.rules`) with `node.disabled = true` / `device.disabled` in `~/.config/wireplumber/wireplumber.conf.d/` hides it from PipeWire/portal consumers; `node.description`/`node.nick` are renameable, `media.role` is not (hard-coded in the v4l2 SPA source). Hiding `/dev/video0` from V4L2 apps needs a udev rule that removes `uaccess` (`TAG-="uaccess", GROUP="camerad", MODE="0660"`) — but PipeWire's v4l2 monitor uses `access(R_OK|W_OK)`, so the user's PipeWire loses it too and the daemon must open the raw device from a privileged path (system user/group, or fd broker). Softer trick: uvcvideo permits one streamer — while the daemon holds STREAMON, other openers get EBUSY. Realistic v1: don't hide, just make the virtual camera the obvious/first choice ("Omarchy Camera") and rename the raw one "(raw)".
- v4l2loopback 0.15.4: dynamic devices via `/dev/v4l2loopback` + `v4l2loopback-ctl add/delete` (0.13+), stricter UAPI (0.14 broke OBS 31.0.x briefly), sysfs `state` (capture/output) but no reader count → detect consumers with fanotify/inotify on the node or `fuser`; obs#12506 (restart fails until module reload) open. PipeWire only creates a node for a loopback if `V4L2_CAP_VIDEO_CAPTURE` is set at probe time (pipewire#3659 open since 2023) — matches the local spike.
- libcamera 0.7.x (GPU SoftISP): IPU6/MIPI laptop cameras have no usable `/dev/videoN` for apps, only libcamera→PipeWire; WirePlumber routes UVC via v4l2 and non-UVC via libcamera. **Reading the source through PipeWire covers both**; direct V4L2 covers UVC only.
- PipeWire 1.5/1.6 added better videoconvert, v4l2 DMABUF-with-modifiers, colorimetry, PeerFormats, but no video loopback/filter module (loopback/filter-chain remain audio-only; ONNX filter-graph in 1.6 is audio). Vulkan video filters are "on the radar". Kernel virtual-camera RFC (Feb 2026) got "use PipeWire" pushback. Christian Schaller (2026-03): background removal "should be a standalone PipeWire tool usable with any camera" — i.e. nobody upstream is building it; the field is open.
- `pw-v4l2` (`pipewire-v4l2` package) LD_PRELOAD shim exists but doesn't survive Chromium's sandboxed capture process — not a system-wide answer.

## 7. Recommended architecture (if built)

```
                 ┌────────────── camfxd (user systemd service, C++/Rust) ──────────────┐
UVC / libcamera  │ pw_stream capture (or V4L2 fallback) → CUDA/ORT effects (mask, depth, │
 ── PipeWire ──▶ │ face, hands) → composite/crop → NV12/YUYV 1080p30                    │
                 │   ├─▶ pw_stream Video/Source, media.role=Camera, fixed EnumFormats     │──▶ portal apps (OBS, flag'd browsers, Snapshot)
                 │   └─▶ v4l2loopback /dev/videoN "Omarchy Camera" (exclusive_caps=1)    │──▶ V4L2 apps (Chromium/Electron/Zoom/Qt/Wine)
                 │ on-demand: run pipeline only while a consumer is attached             │
                 │ control: unix socket / D-Bus + JSON state file (per-camera defaults)  │
                 └────────────────────────────────────────────────────────────────────────┘
                                   ▲ IPC (Quickshell.Io Socket / Process / FileView)
   omarchy-shell plugin `omarchy.camera`: service (watches PW links + daemon state) →
   bar indicator (green camera while any camera in use, like macOS) → panel with
   QtMultimedia preview of /dev/videoN + toggles/sliders (Center Stage, Portrait, Studio
   Light, Background, Reactions), summonable via `omarchy-shell shell summon omarchy.camera`
```

- Language: C++ (PipeWire C API, ORT C++, OpenCV CUDA, direct V4L2 loopback writes) or Rust (`pipewire-rs`, `ort`, custom CUDA/wgpu compositing). Python (`nvidia-broadcast-linux` style) is fine for a prototype but not for a system daemon.
- Enumeration ordering: keep the loopback device *created* at boot (`modprobe.d`, `card_label="Omarchy Camera"`) so V4L2 apps always list it; run the daemon idle and start streaming when `inotify IN_OPEN` fires on the loopback (Windows/macOS-style on-demand). For the PipeWire node, create it at daemon start (it's the daemon's own object; no probe issue).
- Per-camera settings persisted (Windows model) with optional per-app overrides where the app is known (macOS model — PipeWire clients only). Provide a `--raw` opt-out by leaving the raw node visible under a "(raw)" name.
- Effect rollout order by effort: background blur/replace (segmentation) → Center Stage (YuNet + framing rules) → Studio Light (mask-based) → Reactions (hands + overlays) → Presenter Overlay (needs screencast integration).

## 8. Risks / open questions

1. Chromium/Electron PipeWire camera default status — flag still off in M153; keep v4l2loopback until it flips. `pipewire-v4l2` shim doesn't help sandboxed capture.
2. QtMultimedia inside the long-running shell (issue #859 crash with Qt 6.11.0) — mitigate with a lazily loaded plugin or a separate `qs` process for the pane.
3. `pipewiresink mode=provide` bugs on 1.6.x — write the native `pw_stream` provider with fixed formats; verify against Firefox with `allow-pipewire=true` and Chromium with the flag.
4. Truly hiding the raw device from V4L2 apps requires taking uaccess away and a privileged opener; v1 should skip this and rely on naming/default ordering. Note that Zoom/Chromium remember the last chosen device by name.
5. Latency/CPU: MJPEG decode + one H2D + D2H per frame is unavoidable with v4l2loopback (~1080p fine on this box; laptops with iGPU/no CUDA would need a Vulkan/ncnn/OpenVINO backend — this design is NVIDIA-first).
6. Licensing: keep to Apache/MIT/BSD models (MediaPipe seg/hands, YuNet, Depth Anything Small, BiRefNet-lite); RVM is GPL, MODNet weights non-commercial, HaGRID weights unclear, Maxine gated.
7. Local side effect of this research: a stale "OBS Virtual Camera (V4L2)" PipeWire node now exists until WirePlumber restarts (`systemctl --user restart wireplumber`) — harmless.
